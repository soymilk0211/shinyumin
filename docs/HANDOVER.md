## 2. 詞彙表（Domain Glossary）

第 0 步應將本節寫入專案根目錄的 `CONTEXT.md`。

| 詞 | 定義 |
|---|---|
| **商品 Product** | 一款茶（紅玉、阿薩姆、四季春…）。擁有故事、風味描述、照片、分類。**本身不能被購買。** |
| **規格 Variant** | 一款茶的一種包裝，例如「紅玉 四兩・150g 鐵罐」。**這是唯一能被加入購物車的單位**，有自己的價格與販售狀態。未來的禮盒即為新增規格。 |
| **分類 Category** | 單層分類：紅茶／烏龍／綠茶。**紅茶排第一**（招牌商品）。紅玉與阿薩姆是「商品」不是「分類」。 |
| **購物車 Cart** | 只存在瀏覽器 LocalStorage，僅記錄「規格 ID + 數量」，**絕不儲存價格**。 |
| **訂單 Order** | 一次結帳的完整紀錄。 |
| **訂單明細 Order Item** | 訂單中的一個品項，**儲存下單當下的價格快照**。業主改價不得影響歷史訂單金額。 |
| **顧客 Customer** | 目前僅是訂單上的一組聯絡資料，**不是帳號**。以 email 為鑰匙，未來加入會員系統時可自動歸戶。 |
| **後台 Admin** | 密碼保護的繁體中文手機網頁，業主用來改價、切售罄、看訂單、標記出貨。 |

## 7. 通知與 AI 的最終架構

## 8. 已知地雷（都已查證，不要重蹈覆轍）

1. **絕不信任前端傳來的價格。** 購物車在 LocalStorage，可被任意竄改。結帳 API 只接受「規格 ID + 數量」，價格、運費、總額**一律由伺服器重新查詢資料庫計算**。這同時也解決了「顧客隔幾天回來結帳、期間業主改過價」的問題。

2. **絕不動業主現有的 LINE 官方帳號。** LINE 的「回應模式」切成聊天機器人以啟用 Webhook 後，**人工聊天功能會失效**。業主的現有帳號是實際在用的客服管道。已另開一個「御茗內部通知」專用帳號，回應模式設為「關閉手動聊天」。第 5 步還需在後台**關閉「自動回應訊息」並啟用「Webhook」**，否則訊息會被 LINE 攔截、不會轉發。

3. **groupId 無法從任何後台複製。** 必須先接一次 webhook，在群組中發言才能從事件中取得。第 5 步需提供互動式引導。

4. **Resend 必須驗證網域才能寄信。** 不能用 `@ms22.hinet.net`（HiNet 的網域，業主無 DNS 控制權）。

5. **Vercel Hobby 方案禁止商業用途。** 開始收錢前必須升級 Pro（$20/月）。另需開啟 Spend Management 設定花費上限並啟用自動暫停，因為超額後是無上限計費。

6. **DDoS 由 Vercel 自動處理，不需自建。** 但**應用層濫用需要自己防** —— 結帳 API 與後台登入必須加上速率限制，避免假訂單灌爆資料庫或密碼被暴力破解。

7. **Cowork 排程只在 app 開啟時執行。** 業主表示電腦不會關機，可接受。

8. **必須啟用 RLS（Row Level Security），這是 Supabase 最常見的重大疏失。** 預設建立的資料表若未啟用 RLS，任何拿到 `anon` 金鑰的人（該金鑰會出現在瀏覽器端，等同公開）就能讀寫全部資料 —— 包含 `orders` 裡的顧客姓名、電話、地址。要求：
   - **所有資料表一律啟用 RLS。**
   - `categories` / `products` / `variants`：只開放 `anon` **讀取**（且僅限 `is_published` / 未下架者），**不得寫入**。
   - `orders` / `order_items`：`anon` **完全不得讀取或寫入**。所有讀寫一律走伺服器端、使用 `service_role` 金鑰。
   - 顧客送出訂單是經由 Next.js 的 API route（伺服器端），**不是**瀏覽器直接寫資料庫。

9. **金鑰處理規則。** 專案網址（`https://<ref>.supabase.co`）不是機密，它會出現在每一個瀏覽器請求裡。但：
   - `anon` 金鑰：可出現在前端，但必須搭配 RLS 才安全。
   - **`service_role` 金鑰：最高權限，繞過所有 RLS。只能存在於伺服器端環境變數，絕不可進入 GitHub、絕不可出現在任何 `NEXT_PUBLIC_*` 變數、絕不可貼進對話。**
   - 確認 `.env.local` 已被 `.gitignore` 涵蓋，並提供 `.env.example` 範本（只有欄位名稱、沒有值）。

8. **Airtable 已評估並否決。** 免費方案僅 **1,000 次 API 呼叫／月**（不是每秒限速，是每月總量），做網站撐不到一天；且介面**沒有繁體中文**（僅英／法／德／西）。這是改用 Supabase 的主因，不要再提議改回去。

## 10. 視覺方向

- **風格**：現代極簡，藝廊式留白排版
- **色彩**：背景維持清冷極簡（淺色＝薄霧藍系／深色＝午夜紫系），**但所有重點色（按鈕、連結、強調字）使用品牌赭紅**
- **理由**：業主原規格指定紫／藍冷色系，但實際品牌識別（名片、商標）是溫暖的赭紅茶色。純冷色會與實體物料脫節；折衷方案同時保住藝廊感與品牌一致性。
- **實作要求**：所有顏色集中在單一設定檔，方便日後整組更換
- **RWD**：手機與電腦都必須完美適配
- **圖片佔位符**：找不到圖檔時顯示優雅的佔位符，畫面不得崩潰

### 首頁茶湯轉盤（改過四版，記錄為什麼）

右下角那個圓，是「你現在在哪一段」的指示器。

1. **第一版**：隨捲動連續旋轉 + 拖曳盤子等於捲頁面 → 業主回報**超卡**。
   拖曳去捲頁面等於跟瀏覽器搶方向盤；連續轉時外圈的字也對不上內容。
2. **第二版**：外圈的字做成導覽按鈕 → 業主認為「既然盤子能轉就不需要按鈕」。
3. **現在（第三版）**：一段一格。捲進哪一段就轉到那一段，該段落的字轉到
   正上方並以品牌色點亮。字的**底部朝向圓心**，所以正上方那個字是正的。
   一次捲動只做一次 transform，其餘時間完全靜止。
   `pointer-events: none`，完全不吃點擊。捲到頁尾自動淡出。

**第四版（2026-08-18）：不用照片了，而且縮小。**

原本設計成三張茶湯照。業主決定不拍茶湯，所以改成【用 CSS 漸層畫】——
中心亮、邊緣沉、亮點偏左上，本來就是液體在碗裡的樣子，而且永遠不會載入失敗。
茶湯照其實很難拍好：杯緣反光、光線一偏色就跑掉，照片有邊界疊在文字上會顯得髒。

接著業主看實機說「**太大了、字太小、有點廉價**」。他是對的：
- 尺寸從 72vw／560px 縮到 **46vw／372px**（手機 64vw → 56vw）

  —— 極小又極開的字在小尺寸上不會顯得精緻，只會顯得單薄
- 加了**一圈碗沿**（內縮暗環＋上緣陰影）。「廉價」的真正來源是
  邊緣硬切的色塊，看起來像還沒放圖的佔位符

四個段落：開場 `#opening`／工序 `#craft`／主力茶款 `#feature`／更多 `#more`，

### 我踩過的三個坑

**一、症狀修兩次還在，就代表你修錯地方了。**
業主說手機選單很擠，我調了兩次行高與字級都沒用。真正的原因是：
選單列有 `backdrop-blur`，而**帶有 filter／backdrop-filter 的元素會成為
其子孫中 `position: fixed` 的定位基準** —— 那個「全螢幕」選單其實只有
選單列那麼高（72px）。把它移出 header 才真的解決。
**兩次表面修正無效，就去量那個元素的實際尺寸。**

**二、檢查用的瀏覽器分頁是背景執行的，不會繪製畫面。**
`document.visibilityState === "hidden"`、`requestAnimationFrame` 完全不觸發。
因此**CSS 過場、捲動動畫、IntersectionObserver、平滑捲動一律不會執行**。
我曾經以為轉盤壞了、以為換色失效、以為點擊沒反應，全都是這個原因。
**懷疑動畫有問題時，先測 rAF 會不會跑**，再決定要不要動程式。
這類行為只能請業主在真的手機上確認。

**三、不要自己重組向量圖形。**
商標那份 PDF 用裁切遮罩塑形書法字。我自己把向量指令讀出來重組，
結果「御茗」兩個字糊成色塊 —— 而且**結構檢查是通過的，用看的才發現**。
凡是圖形類的產出，一定要真的把圖 render 出來看過。

### 技術上會絆到你的幾件事

- 這版 **Next.js 16 把 middleware 改名為 proxy**（`src/proxy.ts`）。

  只用一種字重是刻意的決定。
- **有 service_role 就能自己讀寫資料**（`scripts/load-products.mjs` 是範例），
